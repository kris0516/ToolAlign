# 04｜评测、指标与统计口径

## 1. 三层评测分开

**L0 实现正确性：** schema、mask、DPO reference、保存加载、白名单、超时、取消、缓存失效。通过说明实现满足测试，不说明模型聪明。

**L1 本地语义执行：** 原创可执行开发运维工具与隐藏 task oracle。建议工具类别：检索版本化文档、查询构建/测试报告、过滤日志、汇总结构化记录、比较兼容规则、单位与数值转换。每类覆盖成功、错误参数、无工具需求、缺少信息和故障恢复。

**L2 外部 benchmark：** 官方 BFCL 评测器支持的固定分类子集。[S12] 先实现能够诚实支持的简单/多工具/无关工具等分类，是否支持多轮以实际 adapter 与依赖为准。首版不承诺完整 V4 所有 agentic 分类。

结果分成 L0/L1/L2 三张表。自建 harness 不能改名叫官方 BFCL；AST 通过不能写成真实业务 API 已执行成功。

## 2. 语义 oracle 设计

Tool runner 只执行允许的固定工具，没有任意 shell/python/SQL。任务真值和 oracle 放在评测侧，与给模型的输入分离。

必须有 counterexample：工具正常返回但选错对象/日期/版本时，任务判失败；多个等价合法策略都应被接受；回答文本自称成功而没有完成目标，仍判失败。模型不作为自己的唯一裁判。

本地任务必须至少有：多步依赖；工具名字相近但语义不同；缺少必要信息应追问或拒答；不需要工具；工具超时/失效后的有限恢复。不把 300 次同模板替换实体包装成 300 个独立问题。

## 3. 指标定义

| 指标 | 分子/分母与关键规则 |
|---|---|
| Raw format validity | 原始输出可按规定解析的样本 / 全部样本；修复后另报 |
| Tool selection accuracy | 工具/无需工具决策符合有效答案集合 / 可判定任务 |
| Argument semantic accuracy | 参数语义符合真值集合 / 指定需调用任务；条件口径另报 |
| Tool execution completion | 未发生执行级失败的调用 / 尝试执行调用，不等于任务成功 |
| Task success rate | oracle 判达成任务 / 所有正式测试任务，包括格式与预算失败 |
| Unnecessary call rate | 不需工具却调用 / 所有不需工具任务 |
| Invalid-tool rate | 未注册或禁止调用 / 所有尝试调用；样本级比例另报 |
| Recovery success | 故障注入后最终达成目标 / 可恢复故障任务；自然错误另报 |
| Budget exhaustion | 达到步数/token/deadline而未完成 / 全部任务 |
| Latency | TTFT、prefill、decode、工具、队列、端到端分别计量 |
| Memory | MLX peak、RSS、系统压力独立显示，不叠加冒充总显存 |

不通过修改分母隐藏 parser failure。非适用项标记 N/A；未运行标记 NOT_RUN。任务超时也必须占端到端成功率分母。

## 4. 冻结实验矩阵

M0：1.7B 原始 checkpoint；M1：同原始模型 + SFT；M2：同 SFT + DPO。固定工具 schema、prompt template、解码、上下文、输出上限、预算和 oracle。

A1：同一选定模型，恢复禁用 vs 启用，预算明确且其额外成本计入。

A2：同一模型、相同请求序列，prefix cache cold/off vs warm/on；不混入不同量化位宽。

扩展 A3：从同一较高精度 checkpoint 导出 8-bit/4-bit；若 adapter fusion 或再次量化引入变化，应单独说明转换流程。

0.6B 模型用于 smoke，完成容量对照后单独表格；不能用 0.6B baseline 对比 1.7B DPO 然后把全部增益归于 DPO。

## 5. 测试隔离和盲审

验证集可重复使用但记录选择次数。最终测试集在模型、超参、prompt、工具实现与 metric 冻结后运行；发现 evaluator bug 可以修，但要提高版本、说明影响并对全部被比较模型重跑。

最终测试失败样本若进入训练，未来必须更换未用过的测试版本；旧测试仅作为回归集。

BFCL 的数据与官方 scorer 均 pin revision；本地 adapter、支持分类、排除原因、超时规则、原始输出 hash 都保存。子集分数不能与官方 overall 排名直接比较。

## 6. 重复与不确定性

十天首轮允许单训练 seed，但明确它只描述一次训练。相同任务集上的配对 bootstrap 给出任务抽样层面的区间；按 group/template 重采样，而不是把同一模板变体当独立样本。它**不能替代多训练 seed 的方差**。

性能计时先区分冷启动和稳态。初期每配置至少 100 请求或报告实际不足的样本数；小样本 P95 标注探索性，不包装成 SLO。相同负载与工具耗时分布，记录失败和排队。

温度、采样 seed、长度分布、CPU/GPU并行任务、插电/电池状态必须入实验记录。速度结果不在实际测量前填数。

## 7. 报告最低要求

给出绝对成功数、总数、比例、按类结果、至少 20 个覆盖不同原因的 bad cases、一个没有改善或退化的分析、质量—成本图表和复现实验入口。

故障注入全通过意味着所测试场景没有违规，不等于“彻底解决幻觉/注入”。DPO 不显著提升也是合法结果；若实现和数据有效，可以解释并发布负结果。

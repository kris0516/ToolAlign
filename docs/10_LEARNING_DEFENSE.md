# 10｜kris 与 Codex 的配合：让项目真正成为自己的能力

## 1. 分工不是“让 AI 把代码写完”

Codex 负责可机械化的实现、接口适配、测试框架、配置与日志整合；kris 对研究问题、数据语义、结果解释与范围决定负责。Supervisor 给出建议和证据，不代替真实人工检查后假称用户审阅。

每天保留一个短学习记录，写“今天能独立解释什么、仍不懂什么、手动检查了哪条样本/错误”。不要以阅读了生成文档代替动手。

## 2. 各阶段本人必须做的最小工作

| 阶段 | 本人检查 | 能回答的问题 |
|---|---|---|
| 契约/数据 | 手看 20 条规范化样本与 group 切分 | 为什么按 schema/template 分组，不只随机切分？ |
| SFT | 标出一条样本哪些 token 进 loss；手改一个 mask 测试 | 为什么 prompt/tool observation 不应全部监督？ |
| LoRA | 列出实际 target modules、rank 与训练参数数目 | 冻结底座为什么仍有激活内存？ |
| DPO | 手算一组 logprob 的 margin/loss，检查 chosen/rejected | reference 为什么是 SFT，停用 adapter 为什么不一定对？ |
| 评测 | 独立判断 20 个含多解和失败的任务 | 执行不报错为何不等于目标完成？ |
| 性能 | 亲自运行一次 cold/warm 对照 | TTFT、prefill、decode、端到端各是什么？ |
| 发布 | 从干净环境跑核心 smoke，讲清一个负结果 | 结果能够推广到哪里，不能推广到哪里？ |

这些数字是工作安排，不是外部招聘标准。没有空完成全部人工检查时，缩实验范围，不让 Codex 伪造“已人工确认”。

## 3. 每个 worker 必须交出的讲解

交接单中说明：输入与输出、关键张量/数据形状、选择该实现的原因、失败如何定位、替代方案为何没选、哪些部分来自上游依赖、哪些是本项目原创。不要求讲解所有胶水代码，但关键算法不能只给安装命令。

## 4. 最终项目表述边界

可依据实测写：Apple Silicon 原生量化 LoRA SFT；已验证的 execution-grounded DPO；版本化数据治理；工具语义评测；缓存/量化对照；可复现部署。

不能无证据写：大规模 RLHF、多机多卡、生产用户规模、已消除幻觉、提升 N%、完整 BFCL 排名、Apple 官方认证、达到某公司的录取标准。

MLX 正式训练不等同于 PyTorch/CUDA 正式训练；独立 PyTorch loss/reference 实现可单独说明。真实负结果和限制比捏造“工业级”更加可防守。

## 5. 二十分钟答辩主线

问题与约束 → 数据与泄漏防护 → SFT/DPO 实现 → 语义 oracle → 控制变量 → 内存/速度 → 失败分析 → 下一步实验。每个结论都指向一个文件、commit 或 run ID，而不是只指向一段聊天。
